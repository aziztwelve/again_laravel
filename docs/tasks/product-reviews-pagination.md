## 1. Цель

На карточке товара покупатель должен иметь возможность последовательно посмотреть
**все доступные для витрины отзывы**, а не только элементы, попавшие в первый ответ
API или в первый видимый экран слайдера.

Под «всеми отзывами» в этой задаче понимаются все отзывы, которые:

- относятся именно к открытому товару;
- опубликованы;
- прошли проверку/модерацию;
- не отмечены как спам;
- не удалены.

Список не должен загружать сотни записей сразу. Первая порция приходит вместе с
SSR-страницей, следующие порции добавляются по явному действию пользователя
«Показать ещё отзывы».

Измеримый результат:

1. При 100 доступных отзывах первый запрос возвращает 8, а пользователь может
   последовательно дойти до 100-го.
2. Уже показанные карточки не исчезают при загрузке следующей порции.
3. UI различает загрузку, пустой результат и ошибку.
4. Публичный API не отдаёт email, служебные статусы, неопубликованные или
   спам-отзывы.
5. Количество SQL-запросов не растёт пропорционально количеству отзывов.

В scope также входят обнаруженные на том же публичном read-path P0-дефекты:
анонимный `admin=true`, утечка PII, отсутствие staff-проверки у операций
публикации/снятия/удаления и неверный actor у like/unlike. Полный редизайн
административного API и продуктовая модель клиентских ответов остаются отдельными
задачами.

## 2. Важная зависимость: пагинация не исправляет неверную привязку данных

На сервере уже обнаружена отдельная причина ситуации «на карточке только один
отзыв»: значительная часть импортированных отзывов привязана к старым,
неактивным или удалённым дублям товаров. Публичная выдача фильтрует по точному
`reviewable_id`, поэтому отзывы старого товара не появятся на активной карточке
даже после идеальной реализации пагинации.

Примеры из [`reviews-full-import.md`](./reviews-full-import.md):

- Sexy AGAIN: старый товар `#48` → активный `#252`;
- Body AGAIN: старый товар `#37` → активный `#241`;
- BOX AGAIN: удалённый товар `#15` → активный `#219`.

Поэтому для бизнес-результата на production необходимо отдельно выполнить и
проверить импорт/перепривязку из `reviews-full-import.md`. Это внешний release
prerequisite для наполненности карточек, но не критерий готовности кода
пагинации: backend/frontend этой задачи тестируются независимо на fixtures.

Диагностическое правило:

- если новый API возвращает `meta.total = 1` и backend-проверка для этого же
  `product_id` также находит один доступный отзыв, интерфейс работает корректно,
  а проблема находится в данных;
- если `meta.total > 1`, но UI показывает только один элемент или не позволяет
  запросить следующую порцию, это дефект данной задачи.

Импорт CSV, дедупликация и перепривязка отзывов **не входят** в эту задачу и не
блокируют её техническую приёмку.

## 3. Что реально происходит сейчас

### 3.1. Текущий поток данных

| Участок | Текущая реализация |
|---|---|
| Страница товара | `again_front/pages/catalog/[slug].vue` подключает `<ProductReviews :product-id="product.id" />` |
| Блок отзывов | `again_front/components/Product/Reviews.vue` |
| Карточка | `again_front/components/Reviews/Card.vue` |
| Запрос витрины | `GET /api/reviews?product_id={id}` |
| Backend | `lara_admin/app/Http/Controllers/Api/Admin/ReviewController.php@index` |
| Фильтры | `lara_admin/app/Traits/ReviewTrait.php::filter_reviews()` |
| Ресурс | `lara_admin/app/Http/Resources/ReviewResource.php` |
| Стили блока | `_reviews.scss`, `_reviews-item.scss` и дополнительные scoped/global-правила внутри Vue-компонентов |

Backend уже использует `paginate()` и по умолчанию отдаёт 10 элементов, а также
поля `current_page`, `per_page`, `total`, `last_page`, `next_page_url` и
`prev_page_url`.

Frontend типизирует только:

```ts
{
  success: boolean
  data: Review[]
}
```

Он не отправляет `page`/`per_page`, игнорирует метаданные и никогда не запрашивает
страницы после первой.

### 3.2. Почему текущий интерфейс создаёт впечатление одного/нескольких отзывов

1. `Product/Reviews.vue` не делает `slice(0, 1)` и рендерит весь полученный
   `reviews.data`. Если в `data` один элемент, ограничение возникло в данных или
   backend-фильтрах, а не во frontend-массиве.
2. Всё после первых 10 записей недоступно, потому что следующая страница не
   загружается.
3. На desktop Swiper показывает 4 карточки, но стрелки навигации скрыты стилями
   при ширине от `992px`. Остальные элементы первой страницы доступны только
   через неочевидное перетаскивание мышью.
4. Кнопка «Показать еще отзывы» уже есть в компоненте, но закомментирована; её
   старый CSS дополнительно скрывает кнопку на tablet/mobile.
5. Один и тот же `v-else` показывает «Отзывов не добавлено» и при пустом ответе,
   и во время загрузки, и при ошибке API.

### 3.3. Технические проблемы backend

- Публичная и административная выдача находятся в одном `Admin\ReviewController`.
- Режим администратора определяется публичным query-параметром `admin=true`, а
  не фактом авторизации сотрудника. Сейчас анонимный запрос может обойти фильтры
  публикации/спама.
- `ReviewResource` отдаёт `client.email` и служебные поля публичному клиенту.
- `ReviewResponseResource` также содержит email пользователей/клиентов.
- `client/profile` не загружаются явно, а `likesCount()` и
  `isLikedByClient()` выполняют запросы из resource для каждого элемента. Это
  N+1 и рост числа SQL-запросов вместе с `per_page`.
- Сортировка `latest()` использует только `created_at DESC`, без уникального
  второго ключа. При одинаковом времени порядок между страницами не определён.
- Параметр `per_page` не имеет верхнего ограничения.

### 3.4. Технические проблемы карточки и стилей

- Продуктовый layout распределён между глобальными SCSS-файлами, scoped-стилями
  карточки и дополнительными global/deep-правилами Swiper.
- Есть дубли `display`, `height`, `margin`; часть legacy-селекторов не используется.
- В раскрытом состоянии текст всё равно ограничен `max-height: 100px` и получает
  внутренний scrollbar — действие «Показать ещё» фактически не раскрывает отзыв.
- Контент выводится через `v-html`, хотя это пользовательский текст. Без
  гарантированной серверной санации это XSS-риск.
- Для рейтинга выводится только `rating` заполненных звёзд; пустые звёзды до пяти
  отсутствуют.
- `ReviewsCard` мутирует `props.review.is_liked`, что нарушает однонаправленный
  поток данных Vue.

## 4. Принятые решения

### 4.1. UX: сетка + «Показать ещё», без продуктового Swiper

В карточке товара отзывы выводятся адаптивной сеткой:

- desktop (`>= 992px`) — 4 колонки;
- tablet (`576–991px`) — 2 колонки;
- mobile (`<= 575px`) — 1 колонка.

Первая порция — 8 отзывов. Это две полные строки на desktop и одинаковый
server-side запрос для всех устройств, без определения viewport на сервере и без
риска SSR hydration mismatch.

Следующая порция добавляется кнопкой **«Показать ещё отзывы»**. Классические
номера страниц не используются: покупателю важнее сохранять контекст чтения, чем
переходить между страницами. Автоматический infinite scroll также не используется:
явная кнопка лучше контролирует трафик, фокус клавиатуры и длину страницы.

Swiper остаётся на главной странице в `Home/Reviews.vue`; эта задача не меняет
layout главного экрана.

### 4.2. Пагинация API

Используется обычная серверная `page/per_page`-пагинация, уже принятая в проекте.

- `per_page` по умолчанию: `8`;
- минимальное значение: `1`;
- максимальное значение: `20`;
- frontend всегда отправляет `per_page=8`;
- сортировка: `published_at DESC`, затем `id DESC`.

Уникальный `id` как второй ключ делает порядок детерминированным для записей с
одинаковым `published_at`.

Legacy-записи с `published_at=null` остаются доступными, но идут после записей с
реальной датой публикации; между собой они также упорядочены по `id DESC`.

Offset-пагинация выбрана ради совместимости с текущей Laravel-архитектурой и
небольшого объёма списка (сотни, а не миллионы записей на товар). Если во время
просмотра модератор опубликует новый отзыв, граница страниц может сместиться;
frontend обязан дедуплицировать элементы по `id`. Полная актуальная выборка
появится после обновления страницы. Для текущей частоты публикаций это приемлемо.

### 4.3. Отдельный публичный endpoint и resource

Канонический endpoint витрины:

```http
GET /api/public/catalog/products/{product}/reviews?page=1&per_page=8
```

Где `{product}` — числовой `products.id` из уже загруженной карточки товара.
Endpoint доступен только для не удалённого товара с `is_active=true`; известный
ID неактивного/удалённого товара возвращает `404`. Это не позволяет обходить
публичный каталог и читать старые дубли напрямую.

В `again_front` transport получает API-base из `DEV_URI`, поэтому ему передаётся
путь **без дополнительного `/api`**:

```text
/public/catalog/products/{id}/reviews
```

Он реализуется отдельными публичными классами и не зависит от query-параметра
`admin`:

- `Api\Public\Review\ProductReviewController`;
- `Public\Review\IndexProductReviewsRequest`;
- `Public\ProductReviewResource`.

Общий административный `ReviewResource` не используется публичным endpoint.

### 4.4. Что остаётся без изменений

- Форма, URL `POST /api/reviews` и успешный moderation flow; меняется только
  минимальная actor/Product-проверка из §6.8.
- Модерация: новый отзыв не добавляется оптимистично в публичный список.
- Лайк/анлайк: `POST /api/reviews/{review}/like` и
  `DELETE /api/reviews/{review}/unlike`.
- Layout/Swiper блока на главной не меняется. Общие исправления самой
  `ReviewsCard` (безопасный текст, пять звёзд, раскрытие и единый формат даты)
  применяются и на главной осознанно.
- `/api/reviews/home-random` сохраняет top-level `{success,data}`, переходит на
  безопасный public resource с ISO-датами; `Home/Reviews.vue` передаёт в card
  `published_at ?? created_at`.
- `Home/Reviews.vue` не мутирует async-data через `.reverse()`: используется
  null-safe `([...(reviews?.data ?? [])].reverse())`/`toReversed()`, сохраняя
  текущий порядок слайдов.
- Визуальный язык карточки: фон, радиус, типографика, красный акцент и текущая
  кнопка «Написать отзыв».

## 5. Целевой API-контракт

### 5.1. Request

```http
GET /api/public/catalog/products/252/reviews?page=1&per_page=8
Accept: application/json
Authorization: Bearer <client-token>   # необязательно, только для is_liked
```

Параметры:

| Поле | Тип | Обязательность | Правила |
|---|---|---|---|
| `page` | integer | нет | default `1`, min `1` |
| `per_page` | integer | нет | default `8`, min `1`, max `20` |

Поля сортировки не принимаются. На первом этапе у публичного списка один
предсказуемый порядок — новые отзывы раньше старых.

Остальные query-параметры (`sort`, `product_id`, `admin` и т.п.) игнорируются и
не меняют выборку/shape; `422` относится к присутствующим невалидным
`page/per_page`. Это поведение фиксируется тестом.

### 5.2. Response `200 OK`

```json
{
  "success": true,
  "data": [
    {
      "id": 1842,
      "content": "Очень удобная модель, размер подошёл.",
      "rating": 5,
      "published_at": "2026-07-09T13:20:00+03:00",
      "created_at": "2026-07-08T18:42:11+03:00",
      "likes_count": 7,
      "is_liked": false,
      "client": {
        "name": "Анна"
      }
    }
  ],
  "meta": {
    "current_page": 1,
    "per_page": 8,
    "total": 117,
    "last_page": 15,
    "has_more": true
  }
}
```

Правила контракта:

- `data` всегда массив;
- `meta.total` — число всех доступных отзывов этого товара, а не размер текущей
  порции;
- `meta.has_more === (current_page < last_page)`;
- на последней странице `has_more=false`;
- `client` может быть `null`; frontend показывает нейтральное имя «Покупатель»;
- публичное `client.name` строится только из `profile.first_name`; фамилия,
  email и внутренний ID не публикуются. Пустое имя также заменяется на
  «Покупатель» на frontend;
- `published_at` может быть `null` у старой опубликованной записи; frontend в
  этом случае показывает `created_at`;
- `created_at` также может быть `null` у legacy/import-записи; если обе даты
  отсутствуют или невалидны, `<time>` не рендерится;
- даты передаются в ISO 8601, форматирование `ДД.ММ.ГГГГ` выполняет frontend;
- `is_liked=false` для гостя и отражает лайк текущего `Client` при валидном
  Sanctum-токене;
- `rating`/`likes_count` сериализуются как integer, `is_liked` — как boolean,
  даты — как ISO 8601 или `null`, независимо от DB-driver casts;
- контракт гарантирует `rating` в диапазоне `1..5`; значение вне диапазона —
  дефект целостности данных, который должен попасть в backend-лог/тест, а
  frontend дополнительно ограничивает число активных звёзд диапазоном `0..5`,
  чтобы повреждённый ответ не создавал произвольное количество SVG;
- `content` считается обычным текстом, а не доверенным HTML. Public resource
  нормализует legacy `<br>/<p>` в переносы строк, удаляет остальные теги и
  возвращает строку; frontend дополнительно экранирует её обычной interpolation.

Публичный resource **не должен** содержать:

- email автора/менеджера;
- `client_id`;
- `is_published`, `is_verified`, `is_spam`, `status`;
- полиморфный `reviewable_type`;
- массив `responses` целиком (его публичное отображение вне scope этой задачи);
- любые поля, нужные только административной таблице.

### 5.3. Ошибки

| Сценарий | HTTP | Поведение frontend |
|---|---:|---|
| Товар не существует/неактивен | `404` | невосстанавливаемая ошибка блока, без retry/ложного empty-state |
| Невалидные `page/per_page` | `422` | невосстанавливаемая ошибка контракта + логирование, без повторения того же запроса |
| Timeout/rate limit | `408/429` | сохранить карточки; не повторять автоматически, разрешить ручной retry; для `429` учитывать `Retry-After`, если он есть |
| Временная ошибка backend | `5xx` | сохранить ранее загруженные карточки; разрешить ручной retry той же страницы |
| Страница больше `last_page` | `200` + пустой `data` | не должно возникать из штатного UI; считать концом списка |

Оборванный запрос через `AbortController` при смене товара не является ошибкой и
не должен показывать пользователю error-state. Остальные неожиданные `4xx`
считаются terminal contract/auth error: без автоматического retry, с технической
диагностикой без вывода backend message в UI.

`next_page_url`/`prev_page_url` не включаются в новый контракт: frontend знает
канонический endpoint и формирует только `product`, `page`, `per_page`. Это не
привязывает клиент к host из backend-конфигурации.

## 6. Backend-архитектура

### 6.1. Route и controller

В публичной группе `Route::prefix('/public')` добавить маршрут:

```php
Route::get('/catalog/products/{product}/reviews', ...);
```

Route ограничивается `->whereNumber('product')`: контракт принимает именно ID,
не slug/uuid.

Controller должен:

1. Получить `Product` через route model binding/явную проверку и после binding
   проверить `is_active === true`; отсутствующий, soft-deleted или неактивный
   товар → `404`. `withTrashed()` на публичном route запрещён.
2. Взять только валидированный `per_page`.
3. Строить запрос от `$product->reviews()`, чтобы нельзя было подмешать чужой
   `product_id` query-параметром.
4. Применить единый scope доступности витрины.
5. Загрузить автора и агрегаты лайков без N+1.
6. Добавить стабильную сортировку с явным null-rank, например
   `CASE WHEN published_at IS NULL THEN 1 ELSE 0 END ASC`, затем
   `published_at DESC, id DESC`. Нельзя полагаться на неявный порядок `NULL` у
   конкретного DB-driver.
7. Вернуть `ProductReviewResource` и нормализованный `meta`.

`ProductReviewResource` явно приводит scalar-типы и даты, а не передаёт значения
модели «как есть». Avatar намеренно не входит в минимальный контракт: в profile
есть `image`, но для него не утверждены public URL/default/privacy semantics;
ошибочный текущий `Client::avatar_url` в новый resource не переносится.

`IndexProductReviewsRequest` обязан иметь `authorize(): true` и валидировать
только query-параметры `page/per_page`. Неизвестный `product_id` из query не
должен влиять на relation, взятую из path.

Сейчас `CatalogController::getProduct()` ищет по slug/uuid без `is_active=true`,
хотя каталог выводит только активные товары. В том же backend-релизе detail и
reviews должны использовать одно правило публичности (`not deleted + active`),
чтобы карточка не открылась успешно с последующим `404` только в блоке отзывов.
Условие detail-запроса должно быть сгруппировано как
`is_active = true AND (slug = ? OR uuid = ?)`: негруппированный `orWhere(uuid)`
не должен позволить открыть неактивный товар по UUID.

В новом public controller/resource не должно быть ветки
`if ($request->get('admin'))`.

### 6.2. Единый scope доступности

В `App\Models\Review\Review` добавить именованный scope, например
`scopeVisibleOnStorefront()`:

```text
is_published = true
AND is_verified = true
AND is_spam = false
AND deleted_at IS NULL
```

SoftDeletes уже добавляет `deleted_at IS NULL`, но требование должно оставаться
явным в тестах. Scope переиспользуется новым endpoint и безопасной публичной
выдачей главной страницы.

Не фильтровать только по строковому `status='published'`: источником истины для
текущей витрины остаются существующие булевы флаги, поскольку legacy/import-данные
могут иметь рассинхрон статуса.

В рамках этой задачи scope обязателен для нового endpoint, `home-random` и обоих
legacy public review endpoints. Сейчас `Product::reviews_count` и
`Product::average_rating` применяют другие условия; их унификация относится к
отдельной задаче про рейтинг-агрегат. Заголовок текущего блока берёт количество
только из `meta.total` и не использует эти legacy-accessors.

Одних флагов Review недостаточно. Для каждого публичного product-review path
обязателен второй predicate: `reviewable_type = Product::class`, связанный Product
не soft-deleted и `is_active=true`.

- новый nested endpoint получает это из уже проверенного `$product`;
- legacy index и `product/{product}` явно проверяют активный Product;
- `home-random` использует `whereHasMorph`/эквивалент и исключает отзывы других
  morph-type и неактивных товаров;
- like/unlike проверяют оба predicate.

Адресный read/action для неактивного или удалённого Product/Review отвечает
`404`, а агрегированный home-list просто исключает такую запись. Нельзя
глобально менять route binding модели Product: административные routes должны
по-прежнему видеть неактивные товары.

### 6.3. Устранение N+1

До пагинации запрос должен использовать:

- eager load автора и профиля: `client.profile`;
- `withCount('likes')` вместо `likesCount()` внутри resource;
- условный `withExists(...)` для лайка текущего клиента либо эквивалентный один
  агрегатный запрос;
- для гостя — вычисляемое `false` без отдельного запроса на каждый отзыв.

Так как route остаётся публичным и не использует обязательный `auth:sanctum`
middleware, опционального покупателя нужно явно резолвить через Sanctum guard.
Нельзя рассчитывать, что default `$request->user()` на публичном route всегда
распознает Bearer-токен. В расчёте `is_liked` участвует только
`App\Models\Client`; staff-токен не считается покупателем.

Ответ содержит персональное поле `is_liked`, поэтому его нельзя кэшировать в
общем CDN/proxy только по URL. В этой реализации endpoint отвечает с
`Cache-Control: private, no-store`; тот же заголовок обязателен для legacy/home
review-ответов, пока они содержат `is_liked`. Один покупатель не должен получить
like-state другого. Если позже понадобится общий CDN-cache, публичные данные и
like-state следует разделить отдельной задачей.

`ProductReviewResource::toArray()` не выполняет запросов к БД. Он только читает
уже загруженные поля/отношения.

Нормализация `content` должна быть одной чистой детерминированной функцией,
переиспользуемой всеми public review-ответами:

1. привести `CRLF/CR` к `LF`;
2. case-insensitive заменить legacy `<br>`, `<br/>` и закрывающий `</p>` на
   перенос строки, открывающий `<p ...>` — удалить;
3. удалить остальные HTML-теги; HTML entities декодировать в обычный текст;
4. убрать недопустимые управляющие символы, не уничтожая переносы/табуляцию;
5. не добавлять HTML escaping в JSON и не обрезать текст: безопасное
   экранирование выполняет Vue interpolation.

Повторное применение нормализатора должно давать тот же результат. Исходное
значение в БД не переписывается.

Ожидание: число SQL-запросов для `per_page=8` и `per_page=20` остаётся
постоянным. Допустимо несколько запросов на paginator, авторов и профиль, но не
`2 × количество отзывов` на likes.

Эта eager-load/aggregate дисциплина относится ко всем public read paths, которые
используют public resource, включая `home-random` и legacy GET, а не только к
новому endpoint.

### 6.4. Индексы и объём

Существующий `morphs('reviewable')` уже создаёт индекс по
`reviewable_type/reviewable_id`. Поэтому в рамках первой реализации не добавлять
спекулятивный составной индекс.

До production-выката выполнить `EXPLAIN` на запросе товара с максимальным числом
отзывов и замер на фактической базе. Если optimizer делает дорогую сортировку или
full scan, отдельной миграцией добавить индекс под фактический WHERE/ORDER BY.
Решение об индексе должно опираться на план запроса, а не только на теорию.

### 6.5. Обязательное устранение публичного admin bypass

Создание нового endpoint само по себе не закрывает старую уязвимость, пока
доступен `GET /api/reviews?admin=true`. В этой же реализации необходимо:

1. На legacy route без `auth:sanctum` явно резолвить actor через
   `Auth::guard('sanctum')->user()`; default `$request->user()` недостаточен.
2. Определять административный режим только для `App\Models\User`, а не по одному
   query-флагу. Точные статусы: нет/невалидный токен + `admin=true` → `401`,
   валидный токен `Client` + `admin=true` → `403`, токен `User` → текущий admin
   response `200`.
3. Для legacy-публичного `GET /api/reviews?product_id=...` временно сохранять
   **текущий top-level контракт** (`success`, `data`, `current_page`, `per_page`,
   `total`, `last_page`, `next_page_url`, `prev_page_url`), но элементы `data`
   сериализовать безопасным public resource и всегда применять storefront scope.
   Public mode валидирует `page/per_page` с максимумом `20`; admin mode имеет
   отдельный максимум `100`. `per_page=100000` даёт `422`, а не огромную
   сериализацию. Legacy GET без `product_id` и без admin actor сохраняет текущий
   HTTP `200 {success:false}` до отдельной contract-миграции.
4. Перевести `/api/reviews/home-random` на безопасный public resource, не меняя
   его визуальное поведение: максимум 10 записей, query-order
   `created_at DESC, id DESC`; frontend сохраняет текущий обратный порядок
   слайдов через немутирующую копию.
5. Не отдавать raw-модели из `GET /api/reviews/product/{product}`. До проверки
   access logs сохранить его прежний top-level JSON-массив и отсутствие
   пагинации, но каждый элемент пропустить через безопасный public resource и
   storefront scope. Перевод этого legacy route на paginated shape или удаление —
   только отдельным релизом после аудита потребителей. Внутри текущих репозиториев
   потребителей не найдено.

Resource выбирается controller-веткой после определения actor, а не query-флагом:

| Ветка | Resource |
|---|---|
| новый product endpoint, public legacy index, `product/{product}`, `home-random` | только `Public\ProductReviewResource` |
| legacy admin index после подтверждённого `App\Models\User` | административный `ReviewResource` |

Сам `ReviewResource` больше не должен вычислять состав полей через
`$request->get('admin')`. Иначе случайный повторный вызов этого resource в
публичной ветке снова откроет служебные поля.

Сохранение legacy top-level shape не обещает молча сохранить все поля элемента.
До backend-релиза access-log аудит фиксирует потребителей
`attributes/images/responses`. Если они нужны внешнему consumer, создаётся
`LegacyPublicReviewResource` только с подтверждёнными безопасными полями; PII и
moderation-поля не сохраняются ни при каком варианте. Разрешённый item-shape
фиксируется snapshot/contract-тестом.

Административный список `again_dashboard` должен продолжить работать для
авторизованного `App\Models\User`. Его перенос на новый `/api/admin/reviews`
можно сделать отдельной задачей; для этой реализации достаточно закрыть анонимный
bypass без поломки текущего dashboard-контракта.

### 6.6. Авторизация административных действий

Текущего `auth:sanctum` недостаточно для `publish`, `unpublish` и `destroy`,
потому что Sanctum-токен есть и у обычного `Client`. Эти операции
должны дополнительно требовать аутентифицированного `App\Models\User`;
покупатель получает `403`. Более гранулярное permission между сотрудниками можно
добавить отдельно, когда для отзывов появится утверждённая матрица прав.

`respond()` намеренно поддерживает и `User`, и `Client`, а схема содержит
`client_id/review_response_id`. Изменение этого продуктового контракта не входит
в пагинацию: риск отсутствия ownership/visibility-проверок фиксируется отдельной
security-задачей, без breaking-запрета клиентских ответов в этом релизе.

Это обязательная часть hardening общего review-контроллера: нельзя закрыть только
чтение `admin=true`, оставив публичную возможность модерировать данные.

### 6.7. Hardening like/unlike

`POST /reviews/{review}/like` и `DELETE /reviews/{review}/unlike` принимают только
actor типа `App\Models\Client`. Токен `App\Models\User` получает `403`, даже если
его числовой ID совпал с ID клиента. Лайк/анлайк разрешён только для отзыва,
который проходит `visibleOnStorefront`; скрытый/spam/удалённый отзыв → `404`.

Это исключает запись staff-ID в `review_likes` и согласует действие карточки с
тем же публичным predicate, что и список.

Unique violation/внутреннее исключение не возвращает пользователю SQL/exception
text. Повторный параллельный like имеет стабильную семантику: идемпотентный
`200` с фактическим `likes_count`; unlike без существующего лайка — также
идемпотентный `200`. Уникальный индекс остаётся последней защитой от гонки.

### 6.8. Минимальный hardening создания отзыва

URL, UX, moderation flow и успешный response `POST /api/reviews` не меняются, но
actor обязан быть `App\Models\Client`; staff User получает `403`. Для product
review допускается только существующий, не удалённый и активный Product; неизвестный
`reviewable_type`, несуществующий ID или неактивный товар дают validation/`404`,
а не `match`/FK `500`. Это закрывает тот же confused-actor класс ошибки, что и
likes, не превращая задачу в редизайн формы.

`respond()` сохраняет dual-actor продуктовый контракт вне scope, однако никакой
catch общего review-контроллера не должен отдавать `line`, stack trace, SQL или
сырой exception message. Ошибка логируется сервером с request ID, наружу уходит
общий `500`.

## 7. Frontend-архитектура

### 7.1. Источник состояния

Пагинационное состояние и запросы выносятся в новый
`composables/useProductReviews.ts`. `Product/Reviews.vue` остаётся владельцем
разметки и получает от composable один согласованный набор состояния:

```ts
items: Review[]
currentPage: number              // 0 до первого успешного ответа
perPage: 8
total: number | null             // null = успешный meta ещё не получен
sessionTotal: number | null
lastPage: number
isInitialLoading: boolean
isLoadingMore: boolean
initialError: unknown | null
loadMoreError: unknown | null
isOutOfSync: boolean
```

Вычисляемые значения:

```ts
hasReviews = items.length > 0
hasInitialResult = total !== null && initialError === null
hasMore = hasInitialResult && !isOutOfSync && currentPage < lastPage
shownCount = items.length
```

Начальное/reset-состояние: `items=[]`, `currentPage=0`, `total=null`,
`sessionTotal=null`, `lastPage=1`, обе ошибки `null`. Именно `total=null`
отличает «ответ ещё не получен» от успешного пустого списка с `total=0`.
Ошибки нормализуются минимум до `{ status: number | null, retryable: boolean,
kind: 'network' | 'http' | 'contract' }`; UI не анализирует произвольную форму
исключения самостоятельно. Terminal load-more error также выключает `hasMore`.

Composable инкапсулирует append/reset/retry и защиту от stale response. Общий
абстрактный paginator для других сущностей в рамках этой задачи не создаётся.

### 7.2. Первая загрузка и SSR

- Первая страница запрашивается с `page=1&per_page=8` во время SSR так же, как
  сейчас загружается карточка товара.
- SSR HTML содержит первую порцию отзывов, корректный empty-state или состояние
  ошибки — в зависимости от фактического результата первого запроса.
- На клиенте не выполняется второй идентичный запрос только из-за hydration.
- Ключ async-data включает `productId`, чтобы данные соседнего товара не
  переиспользовались случайно.
- `useProductReviews` принимает `productId` как `MaybeRefOrGetter<number>`;
  компонент передаёт `toRef(props, 'productId')`. URL, async-data key и reset
  строятся из текущего значения, а не из snapshot при setup.
- SSR payload является единственным источником первой порции при hydration;
  mounted-hook не запускает повторный fetch.

Первая порция содержит персональный `is_liked` и попадает не только в ответ
Laravel, но и в HTML/Nuxt payload. Backend `Cache-Control` сам по себе не
защищает итоговую SSR-страницу. Поэтому product page (и главная, пока
`home-random` запрашивается SSR с Bearer token) обязана выставить на Nuxt response
`Cache-Control: private, no-store` и `Vary: Authorization, Cookie`. Release smoke
двумя разными Client-токенами подтверждает, что HTML/payload одного пользователя
не выдаётся другому. Если потребуется shared-cache страниц, сначала отдельной
задачей разделить общие review-данные и batch like-state; просто снять `no-store`
нельзя.

### 7.3. Загрузка следующей страницы

Текущий `useApi()` оборачивает `useFetch` и предназначен для setup/async-data
lifecycle. Его нельзя заново вызывать из click-handler. Создаётся небольшой
`useApiClient()` — imperative `$fetch`-transport, общий для page 2+, refresh и
like/unlike. Он читает runtime base URL и актуальный auth token **при каждом
вызове**, а не сохраняет token snapshot при setup. Его transport-контракт:

- `DEV_URI + '/public/catalog/products/{id}/reviews'`, без второго `/api`;
- `Accept: application/json`;
- `Authorization: Bearer ...` только при наличии cookie-токена;
- `credentials: 'include'`;
- query `page/per_page`;
- `AbortSignal` для отмены stale-запроса.

Так последующие страницы получают тот же персональный `is_liked`, что и первая
SSR-порция, и не зависят от кэша `useFetch`.

Первая страница вызывается через SSR-aware `useAsyncData/useFetch` lifecycle с
тем же transport builder; imperative client сам по себе не должен создавать
второй hydration-запрос.

Алгоритм `loadMore()`:

1. Немедленно выйти, если `isLoadingMore` или `!hasMore`.
2. Зафиксировать `requestedPage = currentPage + 1`.
3. Заблокировать кнопку и показать состояние «Загрузка…».
4. Запросить тот же product с `requestedPage` и `per_page=8`.
5. После успешного ответа сначала сверить `meta.total` с `sessionTotal`. Если
   total изменился — не добавлять потенциально сдвинутую страницу, включить
   `isOutOfSync` и завершить запрос.
6. При согласованном total:
   - если `data=[]`, хотя `requestedPage <= meta.last_page`, либо порция состоит
     только из уже показанных ID при заявленном `has_more=true`, включить
     `isOutOfSync` и не продвигать page;
   - append-only добавить только первые элементы с ранее не встречавшимся
     `review.id`; существующие карточки не заменять и не переставлять, чтобы не
     затереть локальное like/expand-состояние;
   - обновить `currentPage/total/lastPage` из ответа.
   - вычислить фактический `addedCount` уникальных элементов для live-status.
   - если это последняя страница, проверить `items.length === total`; иначе
     включить `isOutOfSync`.
7. При ошибке:
   - не изменять `currentPage`;
   - не очищать `items`;
   - показать компактную ошибку рядом с кнопкой;
   - повторный клик запрашивает ту же страницу.
8. В `finally` снять блокировку только для актуального request generation.

До изменения состояния JSON проходит runtime-проверку, поскольку TypeScript
interface не валидирует ответ:

- `success === true`, `data` — массив, `meta` присутствует;
- `meta.current_page === requestedPage`, `meta.per_page === 8`;
- `total >= 0`, `last_page >= 1`, `data.length <= per_page`;
- `has_more === (current_page < last_page)`;
- каждый `review.id` — положительный integer.

Нарушение инвариантов не append-ит данные и становится terminal `contract`
error с диагностикой. Abort старого generation игнорируется полностью.

Нельзя увеличивать page заранее без отката и нельзя повторно запрашивать весь
уже загруженный объём через растущий `per_page`.

### 7.4. Смена товара и устаревшие ответы

При изменении `productId`:

- сначала увеличить request generation и abort-нуть старые запросы;
- явно снять старый `isLoadingMore`, чтобы отменённый `finally` не оставил новый
  товар заблокированным;
- очистить список и метаданные;
- сбросить `currentPage` в `0`;
- сбросить `sessionTotal/isOutOfSync`;
- сбросить обе ошибки;
- начать первую загрузку нового товара;
- отменить старый запрос через `AbortController` либо игнорировать его ответ по
  request generation/token.

Ответ предыдущего товара не должен попасть в новый список даже при медленной
сети и быстрой client-side навигации.

Проверка generation/token применяется одинаково в `then`, `catch` и `finally`:
устаревший запрос не вправе добавить данные, записать ошибку или снять loading
уже запущенного запроса нового товара.

### 7.5. Изменение набора между offset-страницами

После первой успешной страницы composable фиксирует `sessionTotal`. Если в
следующей порции `meta.total` изменился либо на финальной странице число
уникальных `items` не совпало с total, установить `isOutOfSync=true`:

- уже прочитанные карточки не удалять автоматически;
- не показывать ложное «Показано N из N»/«Все отзывы показаны»;
- остановить дальнейший load-more;
- показать «Список отзывов изменился» и кнопку «Обновить отзывы»;
- по этой кнопке полностью сбросить состояние и загрузить page 1 заново.

До явного refresh уже показанная часть считается snapshot текущей сессии. Ответ
page 2 сам по себе не позволяет определить, какой элемент page 1 был снят с
публикации, поэтому frontend не пытается угадать и удалить его локально.

В состоянии `isOutOfSync` скрываются и `Показано X из N`, и число в заголовке
`Отзывы (N)`: прежний total уже недостоверен. Остаются карточки, поясняющий
status и CTA обновления.

### 7.6. Типы

В `again_front/types/review.ts` разделить сущность и ответ пагинации:

```ts
export interface ReviewClient {
  name: string
}

export interface Review {
  id: number
  content: string
  rating: number
  published_at: string | null
  created_at: string | null
  client: ReviewClient | null
  likes_count: number
  is_liked: boolean
}

export interface ProductReviewsResponse {
  success: true
  data: Review[]
  meta: {
    current_page: number
    per_page: number
    total: number
    last_page: number
    has_more: boolean
  }
}
```

Не оставлять `client`, `published_at` и `created_at` заведомо non-null, поскольку
backend допускает legacy-записи без автора/дат.

### 7.7. Лайки и локальное состояние карточки

Карточки, добавленные со второй и последующих страниц, должны работать так же,
как первая порция.

- `ReviewsCard` принимает один `review: Review`, а rating/content/name/date/like
  вычисляет внутри. Параллельные props с копиями тех же полей запрещены: они
  способны разойтись при refresh.
- Не мутировать `props.review`.
- `ReviewsCard` инициализирует локальные `isLiked`/`likesCount` из props и считает
  именно `isLiked` текущим источником истины для следующего действия.
- `useReviewLikes.toggleLike()` принимает `reviewId` и текущее boolean-состояние
  явно (либо card вызывает отдельные `likeReview`/`unlikeReview`); он больше не
  выбирает метод по мутируемому объекту review.
- После успешного ответа card инвертирует локальный `isLiked` и берёт
  `likes_count` из backend. При ошибке оба значения остаются прежними.
- Like/unlike используют общий imperative `useApiClient()`, а не вызывают
  `useApi/useFetch` из click-handler.
- Блокировать повторный клик во время запроса.
- Ошибка лайка не должна влиять на пагинацию или удалять карточку.
- Для гостя сохраняется текущий сценарий требования авторизации; его редизайн не
  входит в задачу.

При замене `review` после refresh с тем же `id` watcher синхронизирует локальные
like-значения из новых props, если прямо сейчас нет like-запроса. При смене ID
сбрасываются также expanded/measurement/error. Имя автора проверяется через
`trim()` до fallback «Покупатель».

## 8. UX-состояния

### 8.1. Заголовок

После успешного ответа:

```text
Отзывы (117)
```

Число берётся только из `meta.total`, не из `items.length`. Пока total неизвестен,
показывается просто «Отзывы».

Кнопка «Написать отзыв» остаётся в header на desktop (`>=992px`). На tablet и
mobile (`<=991px`) header-кнопка скрыта, а после состояния списка/ошибки/empty
показывается отдельная полноширинная кнопка, как в текущем поведении.

### 8.2. Initial loading

- При полном SSR первая загрузка ожидается на сервере: браузер сразу получает
  список, empty или error, поэтому skeleton может не успеть отобразиться.
- Skeleton обязателен при client-side смене `productId` и ручной перезагрузке
  первой страницы, когда компонент уже смонтирован и `items` сброшены.
- Не показывать текст «Отзывов не добавлено».
- Показать один адаптивный ряд skeleton-карточек: 4/2/1.
- Для SSR/hydration всегда рендерятся четыре одинаковых skeleton-item, а CSS
  скрывает лишние на tablet/mobile; JS не определяет viewport.
- Для screen reader использовать спокойный статус `aria-live="polite"`:
  «Загружаем отзывы».

### 8.3. Успешный список

- Показать сетку карточек.
- Под сеткой показать `Показано X из N`.
- Если `hasMore=true`, ниже показать кнопку «Показать ещё отзывы».
- Новые карточки добавляются после уже показанных, scroll position не меняется.
- Если следующая страница ещё есть, фокус остаётся на load-more.
- `aria-live="polite"` сообщает фактический результат после дедупликации, например:
  «Добавлено 3 отзыва. Показано 11 из 11».
- Если загружена последняя страница и кнопка исчезает, до её удаления фокус
  переносится на terminal-status с `tabindex="-1"`: «Все 11 отзывов показаны»,
  но только если load-more в этот момент всё ещё был `document.activeElement`.
  Если пользователь уже ушёл Tab/кликом, async response не крадёт фокус.

### 8.4. Loading more

- Существующая сетка остаётся на месте.
- Кнопка disabled и меняет текст на «Загрузка…».
- Допустим существующий модификатор кнопки `_loader _loading`.
- Повторный клик/Enter не создаёт второй параллельный запрос.

### 8.5. Ошибка первой страницы

- Заголовок и кнопка «Написать отзыв» остаются.
- Вместо empty-state показать: «Не удалось загрузить отзывы».
- Для network/`408`/`429`/`5xx` показать `Повторить`, который вручную повторяет
  page `1`; автоматических циклов retry нет.
- Для детерминированных `404/422` retry не показывать: это terminal-state;
  записать техническую ошибку в лог/мониторинг и не зациклить запрос.
- Технический текст ответа/stack trace пользователю не показывать.

### 8.6. Ошибка следующей страницы

- Уже загруженные карточки остаются.
- Рядом с load-more показать: «Не удалось загрузить ещё отзывы».
- Для network/`408`/`429`/`5xx` кнопка меняется на `Повторить` и вручную
  запрашивает ту же страницу.
- Для `404/422` сохранить карточки, остановить пагинацию и зафиксировать
  невосстанавливаемую ошибку контракта без бессмысленного retry.

### 8.7. Пустой список

Только после успешного `200`, когда `data=[]` и `meta.total=0`:

```text
У этого товара пока нет отзывов. Станьте первым, кто поделится впечатлением.
```

Кнопка «Написать отзыв» остаётся доступной. Load-more отсутствует.

### 8.8. Конец списка

Обычный конец списка наступает, когда `has_more=false` и
`items.length === total`:

- кнопку load-more убрать;
- при согласованных данных счётчик показывает `Показано N из N`;
- дополнительные запросы не выполнять.

Если `items.length` и total рассинхронизированы, это не обычный конец списка:
применяется сценарий `isOutOfSync` из §7.5 с кнопкой «Обновить отзывы».

## 9. Карточка отзыва: поведение и безопасность текста

### 9.1. Контент

- Отзыв рендерится как обычный текст через Vue interpolation, не через `v-html`.
- Переносы строк сохраняются через `white-space: pre-line`.
- Длинные слова/URL не создают horizontal overflow (`overflow-wrap: anywhere`).
- По умолчанию текст ограничен пятью строками.
- Кнопка «Показать ещё» отображается только при реальном переполнении.
- После применения clamp переполнение определяется сравнением
  `scrollHeight > clientHeight + epsilon`, а не делением на распарсенный
  `line-height` (значение `normal` даёт `NaN`). Оно пересчитывается после mount,
  при изменении content и ширины карточки через `useResizeObserver`/эквивалент;
  observer/listener обязательно очищается при unmount. До mount toggle скрыт,
  чтобы SSR/hydration разметка совпадала.
- В раскрытом состоянии показывается весь текст по естественной высоте, без
  `max-height: 100px` и внутреннего scrollbar.
- Кнопка «Скрыть» возвращает clamp, имеет `aria-expanded` и `aria-controls` на
  уникальный ID текстового контейнера.

Public resource всегда выдаёт нормализованный plain text: legacy `<br>/<p>`
превращаются в переносы строк, остальные HTML-теги удаляются. Сама БД этой
задачей не переписывается, административный оригинал сохраняется. Нельзя
сохранять `v-html` ради старой разметки. Backend-тест фиксирует `<script>` и
`<img onerror>`; frontend smoke подтверждает, что код не исполняется.

### 9.2. Рейтинг

- Всегда выводить пять звёзд.
- Первые `rating` — активные, остальные — нейтральные/пустые.
- Группа имеет доступное имя `Оценка: N из 5`; сами SVG декоративные
  (`aria-hidden="true"`).

### 9.3. Автор и дата

- Имя: `client.name`, fallback «Покупатель».
- Дата: `published_at`, fallback `created_at`.
- Визуально показывать только дату без времени в формате `ДД.ММ.ГГГГ`.
- Formatter возвращает `{ text, datetime } | null`, а не только display-string;
  `<time :datetime="datetime">{{ text }}</time>` рендерится лишь для валидной
  даты.
- Для одинакового SSR/client результата форматировать с явно заданными
  `ru-RU` и `Europe/Moscow`, а не полагаться на timezone среды выполнения.
- Переходный `formatReviewDate` принимает и новый ISO 8601, и legacy
  `d.m.Y H:i`, чтобы backend-first rollout не показал пользователю сырую дату.
  Legacy-строка разбирается явно по компонентам, а не через непереносимый
  `new Date('11.07.2026 10:30')`.
  Непарсибельное значение не превращается в `Invalid Date`: дата скрывается, а
  ошибка фиксируется в dev/monitoring.
- Legacy `11.07.2026 10:30` нормализуется в валидный datetime
  `2026-07-11T10:30:00+03:00`; `text` собирается с `day/month: '2-digit'` и
  четырёхзначным годом в `Europe/Moscow`.

Like-кнопка имеет `aria-pressed`, динамический `aria-label` («Отметить отзыв как
полезный»/«Убрать отметку…») и `aria-busy` во время запроса; emoji/SVG внутри
декоративен. В продуктовой grid кнопка не оборачивается в `ClientOnly`: count и
`is_liked` уже находятся в SSR payload, поэтому скрывать control и создавать
layout shift не требуется.

### 9.4. Что не добавляется в карточку этой задачей

- фильтры по рейтингу;
- сортировка пользователем;
- фото/лайтбокс отзывов;
- новый дизайн ответов менеджера;
- редактирование отзыва;
- отдельная страница «Все отзывы».

Данные фото и ответов не удаляются из БД/админки; их публичное отображение можно
спроектировать отдельно, не усложняя исправление доступности списка.

## 10. Стили и ответственность компонентов

### 10.1. Разделение стилей

- `Product/Reviews.vue` владеет layout секции: header, grid, loading/error/empty,
  counter и load-more.
- `Reviews/Card.vue` владеет визуалом карточки: текст, звёзды, автор, дата, like,
  expand/collapse.
- Не добавлять новые глобальные селекторы для продуктового layout.
- Удалить obsolete Swiper-разметку и правила только из продуктового блока.
- `_reviews.scss` нельзя удалить целиком: его `.product-reviews__header` и
  `.product-reviews__swiper` использует `Home/Reviews.vue`. В нём сохраняются
  shared/home правила, а только product-only grid/states переносятся в scoped
  `Product/Reviews.vue`.
- При переносе правил из `_reviews-item.scss` сначала обеспечить эквивалентные
  scoped-стили общей карточки, потому что `Home/Reviews.vue` использует тот же
  `ReviewsCard`.

Из `_reviews.scss` переносятся product-only `.product__reviews`, CTA,
`.product-reviews__auth`, `.product-reviews__wrapper` и obsolete
`.product-reviews__more`; shared/home header и swiper-правила остаются.

### 10.2. Сетка

Целевой принцип:

```scss
grid-template-columns: repeat(4, minmax(0, 1fr));
gap: 1.6rem;
```

На tablet — две колонки, на mobile — одна. У grid должен быть
`align-items: start`, чтобы раскрытие длинного текста одной карточки не растягивало
соседние карточки пустым пространством.

Базовый `ReviewsCard` имеет `height:auto; min-height:0`. `height/min-height:100%`
запрещены в product grid и разрешены только контекстным `:deep`-правилом внутри
`Home/Reviews.vue` для равной высоты swiper-slide. Иначе общий card-style отменит
эффект `align-items:start`.

Сохраняются текущие токены и основные значения:

- фон карточки `#F6F5F3`;
- радиус около `2.2rem`;
- красный акцент `var(--fg-red)`;
- переходы `var(--tr-regular)`;
- проектные breakpoints `$tablet` и `$mobile`.

### 10.3. Кнопки

- Для load-more переиспользовать проектную кнопку `btn _border`, а не создавать
  отдельную несовместимую систему.
- Кнопка доступна на desktop/tablet/mobile; старое правило, скрывающее
  `.product-reviews__more` на tablet, удалить.
- `disabled` не должен зависеть только от цвета/opacity.
- Добавить заметный `:focus-visible` outline.
- Все кнопки внутри блока имеют `type="button"`.

Секция имеет связанный с заголовком `aria-labelledby`; сетка размечена как
семантический список, а каждая карточка — как отдельная статья/элемент списка.
Skeleton-карточки декоративны (`aria-hidden`), текстовый live-status передаёт
состояние отдельно.

### 10.4. Адаптив и motion

- На ширине `320px` нет горизонтального scrollbar.
- Header может переноситься, но заголовок/счётчик и CTA не перекрываются.
- Mobile CTA «Написать отзыв» остаётся полноширинным.
- При `prefers-reduced-motion: reduce` раскрытие текста и loading-анимация не
  должны быть обязательны для понимания состояния.

## 12. Обратная совместимость и порядок выката

Порядок обязателен, чтобы frontend не получил `404` и не показал сырые ISO-даты
между релизами:

1. До изменения legacy-контрактов проверить access logs для
   `/api/reviews/product/{product}` и `/api/reviews?product_id=...`. При наличии
   внешних потребителей согласовать миграцию; PII при этом не оставлять ради
   совместимости.
2. Выложить небольшой frontend compatibility slice без переключения product
   endpoint: `formatReviewDate` понимает ISO + legacy, `Home/Reviews.vue`
   использует `published_at ?? created_at`. Остальной редизайн card пока не
   включать.
3. Выложить backend:
   - новый публичный endpoint;
   - безопасный resource;
   - тесты;
   - hardening `admin=true`;
   - временно сохранить описанные совместимые top-level формы legacy GET.
4. Выполнить smoke нового endpoint на товарах с 0, 1 и большим числом отзывов.
5. Выложить основной `again_front`, переключённый на новый endpoint/grid/load-more.
6. Проверить карточку товара и главную страницу.
7. Удаление legacy routes планировать отдельным релизом только после повторной
   проверки access logs.

Access-log проверка операционна: окно минимум 30 дней до изменения и 14 дней
после основного frontend-релиза; отдельно считаются три legacy GET по
caller/user-agent/IP без записи token/query PII. Ответственный за релиз фиксирует
вывод «нет внешних потребителей» или список миграций в release checklist.

Rollback-правила:

- compatibility slice дат не откатывается, пока backend отдаёт ISO;
- основной frontend можно откатить только на compatibility slice;
- новый backend route не удаляется/не откатывается, пока доступна хотя бы одна
  версия frontend, которая его вызывает;
- hardening PII/admin bypass не откатывается — при регрессии делается forward fix;
- после backend hardening очистить CDN/proxy cache старых `/api/reviews*`, где
  мог сохраниться email; Nuxt HTML cache policy проверить отдельно.

### 12.1. Наблюдаемость после выката

Backend structured log/метрики: route, status, latency, `product_id`, page,
`per_page`, request ID и actor type (`guest/client/user`, без actor ID). Frontend:
initial/load-more failure, contract violation, out-of-sync и результат refresh.
Запрещено логировать token, email, имя и content отзыва.

На release window сравнить baseline и первые 24 часа: долю `5xx`, p95 latency,
успех load-more и частоту out-of-sync. Точные alert thresholds задаются от
фактического baseline перед выкладкой; отсутствие dashboard/лог-событий блокирует
production rollout, но не локальную техническую приёмку.

Импорт/перепривязка из `reviews-full-import.md` — внешний production gate для
наполненности карточек. Он может выполняться независимо от code rollout выше и
не входит в техническую приёмку этой спеки.

POST `/api/reviews` нельзя удалить/перенести вместе с legacy GET: он используется
модалкой создания отзыва.

## 13. Тестирование backend

Feature-тесты должны создавать данные фабриками и проверять как минимум:

1. Товар без отзывов → `data=[]`, `total=0`, `last_page=1`, `has_more=false`.
2. Товар с 1 доступным отзывом → одна запись.
3. Ровно 8 → одна страница, кнопке frontend не нужна следующая порция.
4. 9 → первая страница 8, вторая 1, total/last_page корректны.
5. 16 и 17 → корректные границы второй/третьей страницы.
6. Без query применяется default `page=1/per_page=8`; границы `per_page=1` и
   `per_page=20` успешны.
7. `page=0`, нечисловой page, `per_page=0`, `21` и нечисловой per_page → `422`.
8. Страница больше `last_page` → `200`, пустой `data`, согласованный meta.
9. Отзывы другого товара не попадают в ответ.
10. Несуществующий, soft-deleted и `is_active=false` Product → `404` в reviews;
    detail отдельно проверяется по slug и UUID, чтобы `orWhere` не обошёл active.
11. `is_published=false`, `is_verified=false`, `is_spam=true` и soft-deleted
    Review не попадают.
12. Сортировка стабильна при одинаковом `published_at`: больший `id` раньше;
    `published_at=null` идёт после датированных записей.
13. `rating/likes_count` — JSON integer, `is_liked` — boolean, даты — ISO/null.
14. Отсутствующий/soft-deleted Client даёт `client=null`, resource не падает.
15. Legacy HTML нормализуется в plain text; script/event-handler не исполняемы.
16. Гость получает `is_liked=false`.
17. Авторизованный Client получает правильные `is_liked` и `likes_count`.
18. Staff-токен не участвует в `is_liked`, даже если его ID совпал с Client ID.
19. Ответ имеет `Cache-Control: private, no-store`.
20. В JSON отсутствуют email, client ID, moderation-флаги и `responses`.
21. Legacy `GET /api/reviews?product_id=...` сохраняет top-level shape, применяет
    storefront scope и не отдаёт PII.
22. Legacy `GET /api/reviews/product/{product}` сохраняет top-level массив, не
    отдаёт spam/raw model/PII.
23. `home-random` исключает unverified/spam, сохраняет `{success,data}` и не
    содержит email.
24. `GET /api/reviews?admin=true`: без токена → `401`, Client → `403`, User →
    административный `200`.
25. Client не может вызвать `publish`, `unpublish`, `destroy`; разрешённый User
    может. Существующий dual-actor контракт `respond` не ломается этим изменением.
26. Like/unlike: staff token → `403`, скрытый/spam/deleted Review → `404`.
27. При `Model::preventLazyLoading()` сериализация автора/profile не падает.
28. При одинаковом actor и непустом наборе query count для `per_page=20` не
    превышает query count для `per_page=1` более чем на `1`. Отдельный query-count
    test обязателен: `preventLazyLoading()` не ловит явный `likesCount()`.
29. Inactive/soft-deleted Product и `reviewable_type != Product` исключаются из
    обоих legacy GET и `home-random`; like/unlike для них дают `404`.
30. Legacy public `per_page=100000` → `422`, admin `per_page>100` → `422`.
31. Invalid/revoked Bearer на обычном public endpoint трактуется как guest;
    тот же token с `admin=true` не открывает admin mode.
32. `created_at=null` и `published_at=null` сериализуются как `null`, resource не
    падает; frontend скрывает дату.
33. POST review: Client + active Product успешен; staff → `403`, inactive/deleted
    Product и неизвестный type не создают запись.
34. Параллельный/повторный like и unlike отсутствующего лайка имеют стабильный
    идемпотентный response без SQL/exception text.
35. `Cache-Control` и отсутствие PII рекурсивно проверяются у canonical,
    legacy-index, legacy-product и home response.

Boot-хук `Review::creating` безусловно сбрасывает published-поля, поэтому обычный
factory-state с `is_published=true` недостаточен: использовать `afterCreating()`
или явный `update()` после create. Убрать случайные `client_id/reviewable_id` из
fixtures: каждый тест создаёт детерминированные Product/Client и передаёт связи.

## 14. Проверки frontend и ручная матрица

В `again_front` сейчас нет test runner, но одной сборки недостаточно для
generation/abort/retry. В рамках задачи подключается минимальный Vitest и по
возможности выносится чистая часть state machine. Автотесты покрывают:

- double-click и append-only dedupe;
- stale success/error/finally при переходе A → B;
- retry той же page и terminal `404/422`;
- total change, пустую промежуточную и duplicate-only порцию;
- refresh после `isOutOfSync` и reset loading-флагов.

Дополнительно обязательны:

- `npm run build`;
- unit test command из `package.json`;
- ручной smoke в SSR и client-side navigation;
- DevTools Network: первая страница и ровно один запрос на каждый load-more;
- консоль без hydration warnings и Vue warnings о mutation props.

Матрица UI:

| Данные/сценарий | Ожидание |
|---|---|
| 0 отзывов | корректный empty-state + «Написать отзыв» |
| 1 отзыв | одна карточка, без load-more |

## 15. Краевые случаи

- Отзыв сняли с публикации или новый отзыв опубликовали между page 1/page 2:
  изменение total включает `isOutOfSync`; уже прочитанное остаётся snapshot до
  явного «Обновить отзывы».
- `client` удалён/не загружен: карточка не падает, имя «Покупатель».
- `published_at=null` у legacy-записи: показывается `created_at`.
- `content` пустой из legacy-данных: карточка сохраняет метаданные без пустого
  HTML-контейнера; API создания по-прежнему не допускает новый пустой отзыв.
- Backend вернул пустую промежуточную страницу: остановить дальнейшую загрузку и
  включить `isOutOfSync`, не зациклить retry автоматически.
- Если набор одновременно изменился так, что total остался тем же, offset API не
  позволяет это надёжно обнаружить. Дедупликация защищает от повторов, а полная
  актуальность восстанавливается refresh; для текущей частоты модерации это
  принятый компромисс page-пагинации.

## 16. Критерии приёмки

### Данные и API

- [ ] Новый `GET /api/public/catalog/products/{product}/reviews` работает без
      авторизации и принимает валидные `page/per_page`.
- [ ] Endpoint отдаёт только опубликованные, проверенные, не spam и не удалённые
      отзывы точного товара.
- [ ] Неактивный, soft-deleted или отсутствующий Product возвращает `404`.
- [ ] Ответ содержит безопасные `data` и `meta` без email/служебных полей.
- [ ] `total/current_page/last_page/has_more` соответствуют фактическим данным.
- [ ] Порядок стабилен: явный `NULLS LAST`, затем
      `published_at DESC, id DESC`.
- [ ] Верхний лимит `per_page=20` enforced backend-валидацией.
- [ ] `admin=true`: без токена `401`, Client `403`, User `200`; скрытые отзывы и
      PII анонимно не раскрываются.
- [ ] Client не может выполнить `publish/unpublish/destroy`; dual-actor
      `respond` этим релизом не меняется.
- [ ] Like/unlike принимает только Client и только видимый отзыв.
- [ ] POST review сохраняет UX/response, но принимает только Client и активный
      Product; внутренние exception details наружу не выходят.
- [ ] Все public review-ответы имеют `Cache-Control: private, no-store`;
      inactive Product недоступен через legacy/home/like обходы.
- [ ] Нет lazy loading; query-count `per_page=20` отличается от `per_page=1` не
      более чем на один запрос.
- [ ] Для worst-case Product сохранены `EXPLAIN`, фактическая latency и решение
      «существующего индекса достаточно» либо отдельная проверенная миграция.

### UI и поведение

- [ ] Первый SSR-экран загружает не более 8 отзывов.
- [ ] Пользователь может кнопкой дойти до последнего доступного отзыва.
- [ ] Новые порции добавляются, а не заменяют предыдущие.
- [ ] Повторный клик не запускает параллельные запросы и не создаёт дубли.
- [ ] Ошибка следующей страницы не удаляет уже показанные отзывы и допускает
      retry той же страницы только для network/408/429/5xx; `404/422` не зациклены.
- [ ] При смене товара список/page/error полностью сбрасываются; stale response
      не смешивается с новым товаром.
- [ ] Loading, empty, initial error, load-more error и end-state визуально
      различимы.
- [ ] Изменение total между страницами включает `isOutOfSync` и предлагает
      явное обновление без счётчика вида «8 из 7».
- [ ] Сетка 4/2/1 работает без скрытого контента и horizontal overflow.
- [ ] Длинный текст действительно раскрывается полностью и выводится без
      небезопасного `v-html`.
- [ ] Клавиатурный focus, `aria-live`, `aria-expanded`, disabled/loading работают.
- [ ] Итоговые Nuxt product/home SSR responses private/no-store; smoke двух
      клиентов не обнаруживает смешивания персонального `is_liked`.

### Регрессии и сборка

- [ ] Форма «Написать отзыв» открывается и после отправки сохраняет сценарий
      модерации.
- [ ] Like/unlike работает у карточек любой загруженной страницы.
- [ ] Главная сохраняет текущий slider; общая card корректно принимает ISO/legacy
      даты и безопасный plain text.
- [ ] Административный список отзывов работает у авторизованного сотрудника.
- [ ] Backend feature-тесты зелёные.
- [ ] Frontend pagination unit-тесты зелёные.
- [ ] `again_front`: `npm run build` проходит без ошибок.
- [ ] Отдельный runtime SSR/client smoke не показывает hydration/Vue warnings в
      браузерной консоли.
