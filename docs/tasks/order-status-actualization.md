## Важное изменение решения (после обсуждения)

Исходный план (резервирование `reserve` на позициях `customerorder`) был
**заменён** на более простую и надёжную схему после того, как тесты показали
проблему: резерв не защищал от перепродажи на сайте (сайт проверяет остаток
по локальному `stock_quantity`, а не по резерву в МойСклад), и переход в
статус «Отгружен» сам сбрасывал резерв без физического списания.

**Принято решение:** товар списывается **сразу при создании заказа**
(независимо от оплаты) через документ «Отгрузка» (`demand`), а не
резервируется. Если оплата не поступает за 2 часа — товар возвращается на
склад (демонд распроводится). Это можно грубо описать так: «Новый заказ
на сайте = списание на складе сразу», а не «резерв → списание при
отгрузке».

**Что это означает для нерешённых пунктов 1-2, 5:**
- Логика для статуса «Отгружен» из исходного плана («создать `demand` при
  переходе в Отгружен») **больше не актуальна** — списание происходит
  раньше, при создании. Статус «Отгружен» теперь просьто отражает, что
  сервис доставки забрал заказ, без дополнительной складской операции.
- Статус «Возврат товара» по-прежнему **не реализован** — при возврате
  товара от клиента нужно решить (см. открытый вопрос №4), распроводить
  тот же `demand`, или создавать отдельный документ `salesreturn`.

## Реализовано (детали)

### 3. Синхронизация с МойСклад — списание сразу при заказе

- **`App\Services\MoySklad\DemandService`** (новый сервис):
  - `shipOrder(Order $order): string` — создаёт и проводит документ
    «Отгрузка» (`demand`), привязанный к заказу через `customerOrder`.
    Идемпотентно (хранит `moysklad_demand_uuid` на заказе, повторный вызов
    не создаёт дубль).
  - `returnOrderStock(Order $order): void` — распроводит существующий
    `demand` (`applicable: false`), возвращая товар на склад без удаления
    документа. Идемпотентно (если демонда нет — не делает ничего).
- **`App\Jobs\SyncOrderToMoySkladJob`** — после `pushOrder()` (создание/
  обновление `customerorder`) вызывает `DemandService::shipOrder()`, если
  заказ не отменён.
- **`App\Jobs\ReturnOrderStockToMoySkladJob`** (новый Job) — асинхронно
  вызывает `returnOrderStock()`.
- **`OrderCreationService::cancelOrder()`** — при отмене (любой, в т.ч. от
  крона) ставит `ReturnOrderStockToMoySkladJob` в очередь, если у заказа
  есть `moysklad_demand_uuid`.
- **Резерв убран** из `OrderService::buildPositions()` — позиции
  `customerorder` больше не передают поле `reserve`.
- Новая колонка `orders.moysklad_demand_uuid` (миграция
  `2026_08_19_074500_add_moysklad_demand_uuid_to_orders_table.php`).

**Подтверждено тестами на реальных данных (не эмуляция):**
- Создание заказа на 2 шт → физический остаток в МойСклад `100 → 98`.
- Отмена того же заказа → остаток `98 → 100`, лог:
  `MoySklad: товар возвращён на склад (demand распроведён)`.
- `check_stock()` (используется синхронизацией товаров) переключён на
  отчёт `/report/stock/all` (отдаёт `stock`, `reserve`, `quantity`), но
  раз резерва больше нет, `stock` в результате практически всегда равен
  физическому остатку — оставлено как есть, задел на будущее если резерв
  понадобится снова.

### 4. Крон-автоотмена неоплаченных заказов (2 часа)

- **`App\Console\Commands\CancelUnpaidOrdersCommand`**
  (`orders:cancel-unpaid`) — находит заказы `status = new` и
  `payment_status != paid`, созданные более 2 часов назад, отменяет через
  существующий `cancelOrder()` (который уже обновляет статус в МойСклад и
  запускает возврат товара).
- Зарегистрировано в `routes/console.php`:
  `Schedule::command('orders:cancel-unpaid')->everyFiveMinutes()->withoutOverlapping()->runInBackground()`.

**Подтверждено тестом:** заказ с искусственно состаренной `created_at`
(-3 часа) был найден командой, отменён, товар возвращён на склад
(`stock` восстановлен полностью).

## Побочная находка (не входит в скоуп задачи, требует отдельного решения)

При тестировании `cancelOrder()` выявлено: поля `cancellation_reason` и
`cancelled_at`, которые метод пытается записать через `$order->update([...])`,
**не существуют как колонки в таблице `orders`** — Eloquent их тихо
игнорирует (Mass Assignment не бросает ошибку на отсутствующий в `$fillable`/
несуществующий столбец в некоторых конфигурациях). Причина/возраст баге не
исследован. Не мешает работе МойСклад-синхронизации (статус `cancelled`
сохраняется корректно), но причина отмены сейчас нигде не фиксируется в БД.
Нужно отдельно решить: добавить колонки миграцией, или это уже где-то
пишется иначе (например, через `OrderHistoryService`).

## Описание (исходное, из ТЗ)

**Сценарий:** админка → заказы → все заказы → карточка заказа.

Актуализировать список статусов заказа и логику их переключения, синхронизировав
это с интеграцией МойСклад (резервирование/списание остатков) и вебхуком
CloudPayments (возврат оплаты).

### Факт (было на момент постановки задачи)

Текущий список статусов (`App\Enums\OrderStatus`):

```
Новый, В работе, Отгружен, Отгружен на экспорт, Доставлен, Отменен, Возврат товара
```

Логика переключения по большей части ручная (менеджер сам меняет статус в
интерфейсе), кроме:
- Смена `payment_status` на `paid` при вебхуке CloudPayments `pay` → диспатчит
  `OrderPaid`, который ставит в очередь создание доставки (Яндекс/СДЭК) и
  синхронизацию с МойСклад (см. `SyncOrderToMoySkladAfterPayment`).
- `cancelOrder()` меняет статус на `cancelled` и (если заказ уже выгружен в
  МойСклад) обновляет `state` документа там же на статус «Отменен».

### План-результат (исходный)

**1. Список статусов** (`App\Enums\OrderStatus`):

```
Новый → В работе → Отгружен → Доставлен → Отменен → Возврат товара → Возврат оплаты
```

- Убрать: `Отгружен на экспорт` (`SHIPPED_EXPORT`).
- Добавить в конец: `Возврат оплаты` (новый case, отдельно от существующего
  `PaymentStatus::REFUNDED`, который относится к статусу *платежа*, не заказа).

**2. Логика по каждому статусу:**

| Статус | Кто/что переключает | Описание |
|---|---|---|
| Новый | Автоматически при создании заказа | Как сейчас |
| В работе | Менеджер вручную в админке | Как сейчас |
| Отгружен | Автоматически — когда служба доставки (ЯД/СДЭК) забрала заказ и оформила у себя на складе/в своей системе | Заказ считается физически покинувшим склад |
| Доставлен | Автоматически — когда доставлено в ПВЗ или на адрес клиенту | Финальный успешный статус |
| Отменен | Автоматически — если после оформления заказа в течение 2 часов не произошла оплата | Требует: возврат/списание товара в МойСклад + смена статуса заказа |
| Возврат товара | Автоматически — клиент не забрал заказ из ПВЗ / не забрал товар дома, заказ вернулся отправителю (по данным ЯД/СДЭК) | |
| Возврат оплаты | Менеджер вручную через кнопку в карточке заказа | Клиент отказался от покупки после оплаты — ручной возврат денег через CloudPayments |

**5. Кнопка «Отменить оплату» (Возврат оплаты):**

- Новая кнопка в карточке заказа в админке (`again_dashboard`), видна при
  `payment_status = paid` (или соответствующих статусах заказа).
- По клику — вызов `POST /api/webhooks/cloudpayments/refund`.
- Существующий метод `CloudPaymentProvider::refundPayment()` уже умеет
  делать возврат через API CloudPayments (`POST /payments/refund`) и
  переводить `Payment::status` в `REFUNDED` — не хватает только: (а)
  admin-эндпоинта, который его вызывает, (б) обновления `Order::status` на
  новый статус «Возврат оплаты» после успешного возврата.

## Открытые вопросы (требуют уточнения перед реализацией пунктов 1, 2, 5)

1. **Эндпоинт `/api/webhooks/cloudpayments/refund`** — это:
   - (a) новый вебхук, который слушает **уведомление от CloudPayments** о
     совершённом возврате (аналог `pay`/`fail`), а кнопка в админке дёргает
     **другой**, admin-only эндпоинт, который инициирует возврат через API
     CloudPayments, и в ответ на успех CloudPayments сам присылает вебхук на
     этот путь?
   - (b) или сам этот путь и должен вызываться прямо кнопкой из дашборда
     (тогда он должен быть защищён admin-авторизацией, а не публичным
     webhook-роутом без CSRF/подписи)?
   - Текущие вебхуки CloudPayments (`check`, `pay`, `fail`) — публичные,
     проверяются подписью `Content-HMAC` от CloudPayments, а не
     пользовательской сессией. Смешивать ручное действие менеджера с этим
     механизмом напрямую — рискованно.

2. **Порядок статусов при автоотмене:** если заказ не оплачен за
   2 часа — сразу `Отменен`, минуя `В работе`? Что делать, если заказ **уже**
   в статусе «В работе» без оплаты дольше 2 часов — тоже отменять?
   (Текущая реализация крона проверяет **только** `status = new` — заказы в
   «В работе» без оплаты крон не трогает.)

3. **«Возврат товара»** — как технически определяется момент возврата
   (по вебхуку/статусу от ЯД/СДЭК, или тоже вручную менеджером)? В задаче
   написано «заказ возвращается отправителю у ЯД, СДЭК» — предполагается
   автоматическое определение через API служб доставки, но текущая
   интеграция (`YandexDeliveryService`, `CdekDeliveryService`) может не
   отслеживать этот статус — нужно проверить, какие статусы вообще
   присылают эти сервисы через свои вебхуки/поллинг
   (`PollYandexDeliveryStatusesJob`, `PollCdekDeliveryStatusesJob`).

4. **Демонд (`demand`) при возврате товара:** раз списание теперь
   происходит сразу при создании заказа (а не при отгрузке), к моменту
   «Возврат товара» демонд почти наверняка уже существует и проведён.
   Нужен ли отдельный документ **возврата от покупателя** (`salesreturn`)
   вместо простого распроведения того же `demand`? Технически распроведение
   технически работает (подтверждено тестом), но бухгалтерски может быть
   некорректно смешивать «просто отменённый до отгрузки заказ» и «клиент
   вернул уже полученный товар» — это разные бизнес-события, для второго в
   МойСклад может быть предпочтительнее отдельный тип документа.

5. **Обратная совместимость данных:** уже есть заказы со статусом
   `shipped_export`, если такие есть в БД — что с ними делать при удалении
   этого case из enum (перевести в `shipped`? оставить как legacy-значение
   без case в enum?). **Нужно выполнить перед удалением case из enum:**
   `SELECT COUNT(*) FROM orders WHERE status = 'shipped_export'` — если > 0,
   решить миграцию данных.

### МойСклад — подтверждённые фактами (тестами) детали API

- Резерв позиции заказа: `PUT /entity/customerorder/{id}/positions/{positionId}`
  с телом `{"reserve": N}` — не влияет на физический остаток (`stock`),
  влияет на «доступное количество» (`quantity` в отчёте
  `/report/stock/all`, где `quantity = stock - reserve`). **Больше не
  используется в текущей реализации** (решение изменено на прямое списание).
- Отчёт `/report/stock/all/current` **не отдаёт** `reserve` — только
  физический `stock`. Отчёт `/report/stock/all` отдаёт оба поля плюс
  посчитанное `quantity` (доступно). Используется в
  `MoySkladHelperService::check_stock()`.
- Смена `state` документа `customerorder` на статус со `stateType:
  Unsuccessful` (например, «Отменен») **автоматически снимает резерв**, если
  он был. С текущей реализацией (без резерва) это не имеет значения для
  остатков — товар возвращается через отдельный вызов `returnOrderStock()`.
- Смена `state` на «Отгружен» (`stateType: Regular` в этом аккаунте) **тоже
  снимает резерв**, но **не списывает** физический остаток сама по себе —
  требуется отдельный документ `demand`.
- Физическое списание: `POST /entity/demand` с обязательными
  `organization`, `agent`, `store` (получить через `GET /entity/store`),
  опционально `customerOrder` (привязка к заказу), `positions`.
  `demand.applicable: true` — списывает остаток, `false` — распроводит
  (возвращает остаток обратно, документ не удаляется). **Реализовано** в
  `DemandService`.
