# Задача: Актуализация статусов и логики карточки заказа

**Статус:** Требует уточнений — открытые вопросы ниже
**Дата:** 2026-08-19
**Раздел админки:** Заказы → Все заказы → карточка заказа

---

## Описание

**Сценарий:** админка → заказы → все заказы → карточка заказа.

Актуализировать список статусов заказа и логику их переключения, синхронизировав
это с интеграцией МойСклад (резервирование/списание остатков) и вебхуком
CloudPayments (возврат оплаты).

### Факт (сейчас)

Текущий список статусов (`App\Enums\OrderStatus`):

```
Новый, В работе, Отгружен, Отгружен на экспорт, Доставлен, Отменен, Возврат товара
```

Логика переключения переключения по большей части ручная (менеджер сам меняет
статус в интерфейсе), кроме:
- Смена `payment_status` на `paid` при вебхуке CloudPayments `pay` → диспатчит
  `OrderPaid`, который ставит в очередь создание доставки (Яндекс/СДЭК) и
  синхронизацию с МойСклад (см. `SyncOrderToMoySkladAfterPayment`).
- `cancelOrder()` меняет статус на `cancelled` и (если заказ уже выгружен в
  МойСклад) обновляет `state` документа там же на статус «Отменен».

### План-результат

**1. Список статусов** (`App\Enums\OrderStatus`):

```
Новый → В работе → Отгружен → Доставлен → Отменен → Возврат товара → Возврат оплаты
```

- Убрать: `Отгружен на экспорт` (`SHIPPED_EXPORT`).
- Добавить в конец: `Возврат оплаты` (новый case, отдельно от существующего
  `PaymentStatus::REFUNDED`, который относится к статусу *платежа*, не заказа).

**2. Логика по каждому статусу:**

| Статус | Кто/что переключает | Описание |
|---|---|---|
| Новый | Автоматически при создании заказа | Как сейчас |
| В работе | Менеджер вручную в админке | Как сейчас |
| Отгружен | Автоматически — когда служба доставки (ЯД/СДЭК) забрала заказ и оформила у себя на складе/в своей системе | Заказ считается физически покинувшим склад |
| Доставлен | Автоматически — когда доставлено в ПВЗ или на адрес клиенту | Финальный успешный статус |
| Отменен | Автоматически — если после оформления заказа в течение 2 часов не произошла оплата | Требует: возврат/списание товара в МойСклад + смена статуса заказа |
| Возврат товара | Автоматически — клиент не забрал заказ из ПВЗ / не забрал товар дома, заказ вернулся отправителю (по данным ЯД/СДЭК) | |
| Возврат оплаты | Менеджер вручную через кнопку в карточке заказа | Клиент отказался от покупки после оплаты — ручной возврат денег через CloudPayments |

**3. Синхронизация с МойСклад:**

- При создании заказа — товар резервируется в МойСклад (уже реализовано,
  см. `OrderService::pushOrder()` → `reserve` на позициях документа
  `customerorder`).
- **Открытый вопрос:** при переходе в «Отгружен» — нужно явно создавать
  документ «Отгрузка» (`demand`) в МойСклад, привязанный к заказу через
  поле `customerOrder`, чтобы товар физически списался со склада.
  Подтверждено тестом: смена `state` документа `customerorder` на
  «Отгружен» **не списывает** физический остаток — только снимает резерв.
  Нужен отдельный `POST /entity/demand` с полями `organization`, `agent`,
  `store`, `customerOrder`, `positions`.
- При отмене (по любой причине — неоплата за 2ч, либо ручная) —
  МойСклад-документ должен получить статус «Отменен», резерв снимается
  автоматически (подтверждено тестом). Если к этому моменту уже был создан
  `demand` (отгрузка) — его нужно распровести (`applicable: false`), чтобы
  вернуть товар физически на склад (подтверждено тестом: `applicable: false`
  откатывает списание).

**4. Крон-задача (2 часа без оплаты → автоотмена):**

- Проверять заказы со статусом `Новый`, у которых `payment_status != paid`
  и `created_at` старше 2 часов.
- Переводить в статус `Отменен`.
- Снимать резерв/списание в МойСклад (см. пункт 3).
- Технически: `App\Console\Commands\*` + запись в `routes/console.php`
  (расписание) или `bootstrap/app.php` в зависимости от версии Laravel в
  проекте — уточнить, где регистрируется существующий scheduler
  (`laravel-scheduler` pm2-процесс уже работает, значит `withSchedule`/
  `Schedule` уже используется — найти и добавить туда).

**5. Кнопка «Отменить оплату» (Возврат оплаты):**

- Новая кнопка в карточке заказа в админке (`again_dashboard`), видна при
  `payment_status = paid` (или соответствующих статусах заказа).
- По клику — вызов `POST /api/webhooks/cloudpayments/refund` (**внимание**:
  несмотря на префикс `webhooks/`, судя по формулировке задачи, этот роут
  должен быть достижим и как ручное действие менеджера, не только как
  вебхук от CloudPayments — нужно уточнить, кто и как его будет вызывать:
  сам дашборд напрямую, или отдельный admin-роут, который внутри вызывает
  `CloudPaymentProvider::refundPayment()`).
- Существующий метод `CloudPaymentProvider::refundPayment()` уже умеет
  делать возврат через API CloudPayments (`POST /payments/refund`) и
  переводить `Payment::status` в `REFUNDED` — не хватает только: (а)
  admin-эндпоинта, который его вызывает, (б) обновления `Order::status` на
  новый статус `Возврат оплаты` после успешного возврата.

## Открытые вопросы (требуют уточнения перед реализацией)

1. **Эндпоинт `/api/webhooks/cloudpayments/refund`** — это:
   - (a) новый вебхук, который слушает **уведомление от CloudPayments** о
     совершённом возврате (аналог `pay`/`fail`), а кнопка в админке дёргает
     **другой**, admin-only эндпоинт, который инициирует возврат через API
     CloudPayments, и в ответ на успех CloudPayments сам присылает вебхук на
     этот путь?
   - (b) или сам этот путь и должен вызываться прямо кнопкой из дашборда
     (тогда он должен быть защищён admin-авторизацией, а не публичным
     webhook-роутом без CSRF/подписи)?
   - Текущие вебхуки CloudPayments (`check`, `pay`, `fail`) — публичные,
     проверяются подписью `Content-HMAC` от CloudPayments, а не
     пользовательской сессией. Смешивать ручное действие менеджера с этим
     механизмом напрямую — рискованно.

2. **Порядок статусов при автоотмене (пункт 4):** если заказ не оплачен за
   2 часа — сразу `Отменен`, минуя `В работе`? (Судя по задаче — да, но
   явно не написано, что делать, если заказ **уже** в статусе «В работе» без
   оплаты дольше 2 часов — тоже отменять?)

3. **«Возврат товара»** — как технически определяется момент возврата
   (по вебхуку/статусу от ЯД/СДЭК, или тоже вручную менеджером)? В задаче
   написано «заказ возвращается отправителю у ЯД, СДЭК» — предполагается
   автоматическое определение через API служб доставки, но текущая
   интеграция (`YandexDeliveryService`, `CdekDeliveryService`) может не
   отслеживать этот статус — нужно проверить, какие статусы вообще
   присылают эти сервисы через свои вебхуки/поллинг
   (`PollYandexDeliveryStatusesJob`, `PollCdekDeliveryStatusesJob`).

4. **Демонд (`demand`) и повторные операции:** если заказ вернулся
   («Возврат товара») **после** того, как уже был создан и проведён
   `demand` (товар списан) — нужен ли отдельный документ **возврата от
   покупателя** (`salesreturn`) вместо простого распроведения `demand`?
   Технически это более корректный путь в бухгалтерском смысле (нельзя
   просто "отменить" реально произошедшую отгрузку toward клиента, для
   этого есть отдельный тип документа), но требует дополнительного
   исследования API.

5. **Обратная совместимость данных:** уже есть заказы со статусом
   `shipped_export`, если такие есть в БД — что с ними делать при удалении
   этого case из enum (перевести в `shipped`? оставить как legacy-значение
   без case в enum?).

### МойСклад — подтверждённые фактами (тестами) детали API

- Резерв позиции заказа: `PUT /entity/customerorder/{id}/positions/{positionId}`
  с телом `{"reserve": N}` — не влияет на физический остаток (`stock`),
  влияет на «доступное количество» (`quantity` в отчёте
  `/report/stock/all`, где `quantity = stock - reserve`).
- Отчёт `/report/stock/all/current` **не отдаёт** `reserve` — только
  физический `stock`. Отчёт `/report/stock/all` отдаёт оба поля плюс
  посчитанное `quantity` (доступно). Используется в
  `MoySkladHelperService::check_stock()` (уже переключено на верный отчёт).
- Смена `state` документа `customerorder` на статус со `stateType:
  Unsuccessful` (например, «Отменен») **автоматически снимает резерв**
  (подтверждено тестом).
- Смена `state` на «Отгружен» (`stateType: Regular` в этом аккаунте) **тоже
  снимает резерв**, но **не списывает** физический остаток — резерв просто
  пропадает без физического списания. Это подтверждённый факт, который
  нужно учитывать при реализации пункта 3 плана-результата.
- Физическое списание: `POST /entity/demand` с обязательными
  `organization`, `agent`, `store` (получить через `GET /entity/store`),
  опционально `customerOrder` (привязка к заказу), `positions`.
  `demand.applicable: true` — списывает остаток, `false` — распроводит
  (возвращает остаток обратно, документ не удаляется).
