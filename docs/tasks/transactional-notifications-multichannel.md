# Задача: единые транзакционные уведомления в Email, Telegram, MAX и VK

**Статус:** решения утверждены — к реализации  
**Дата:** 2026-07-14  
**Backend:** `lara_admin`  
**Связанные задачи:**
- `docs/tasks/abandoned-cart.md` — цепочка брошенной корзины;
- `docs/tasks/order-card-chats.md` — уведомления о заказах, подарочных картах и
  зеркалирование в переписку;
- `docs/tasks/messenger-deeplink-binding.md` — привязка мессенджеров к клиенту
  и заказу.

---

## Цель

Все клиентские транзакционные события должны отправляться во **все доступные
каналы клиента одновременно**:

- Email;
- Telegram;
- MAX;
- VK.

SMS в задачу не входит: зарегистрированного SMS-канала в
`NotificationService` сейчас нет. WhatsApp также не входит в утверждённый
целевой список.

Если у клиента доступно несколько каналов, сообщение не выбирает один
приоритетный канал, а дублируется в каждый доступный канал. Отсутствие или сбой
одного канала не должны блокировать остальные.

### Основные точки кода

- `app/Services/Notifications/NotificationService.php` — зарегистрированы
  Email, Telegram, MAX, WhatsApp, VK и Web Chat.
- `app/Services/Notifications/OrderNotificationService.php` — заказы и
  подарочные карты; получатели сейчас Email + Telegram + MAX, без VK.
- `app/Services/Cart/AbandonedCartService.php` — брошенная корзина; метод
  `resolveChannel()` выбирает только один канал по приоритету.
- `app/Jobs/NotifyRestockSubscribersJob.php` — рабочий пример независимой
  отправки Email + Telegram + MAX + VK.
- `app/Console/Commands/BirthdayDiscountCommand.php` — каналы собраны
  разрозненно, MAX отсутствует.
- `app/Services/Notifications/Jobs/SendNotificationJob.php` — отдельная задача
  очереди на канал.

## Утверждённая модель

### 1. Единый резолвер получателей

Ввести сервис, например:

`App\Services\Notifications\CustomerChannelResolver`

Он принимает `Client` и, при необходимости, fallback-данные заказа/корзины и
возвращает нормализованный список:

```php
[
    ['channel' => 'email',    'recipient_id' => 'client@example.com'],
    ['channel' => 'telegram', 'recipient_id' => '123456'],
    ['channel' => 'max',      'recipient_id' => '987654'],
    ['channel' => 'vk',       'recipient_id' => '741503435'],
]
```

Источники контактов:

- Email: `client.email`, fallback — `order.email`;
- Telegram: `profile.telegram_chat_id`, fallback — `telegram_user_id`;
- MAX: `profile.max_user_id`;
- VK: `profile.vk_user_id`.

Пустые значения исключаются, одинаковые пары `channel + recipient_id`
дедуплицируются.

### 2. Независимая отправка по каналам

Для каждого доступного получателя создаётся отдельный `SendNotificationJob`.
Ошибка Telegram не отменяет Email/MAX/VK. Результаты логируются по каждому
каналу отдельно.

### 3. Форматы сообщений

- Email может получать HTML-шаблон (`data.html`) и отдельную тему.
- Telegram, MAX и VK получают компактный plain-text вариант с теми же данными
  и ссылками.
- Бизнес-содержание одного события собирается одним builder/service, чтобы
  тексты каналов не расходились.

### 4. Зеркалирование в переписку

Успешные уведомления Telegram/MAX/VK и при необходимости Email зеркалируются в
`Conversation`/`Message` через существующий механизм
`mirror_conversation`. Для заказных событий в `source_data` сохраняется
`order_id`; для брошенной корзины — `cart_id`, `notification_type` и `step`.

### 5. Идемпотентность

- Заказ/подарочная карта: защита от повторной постановки одного события в один
  канал (`event type + entity id + channel + recipient`).
- Брошенная корзина: идемпотентность должна учитывать канал. Текущий UNIQUE
  `cart_id + step` недостаточен для четырёх отправок; журнал должен позволять
  по одной записи на `cart_id + step + channel`.
- Повтор job после временной ошибки не создаёт вторую коммуникацию.

## Изменения по событиям

### Новый заказ

Расширить `OrderNotificationService::customerRecipients()` через единый
резолвер и добавить VK. Вызывать одинаково после заказа с витрины и из админки.

### Подарочные карты

`notifyGiftCardIssued()` и `notifyGiftCardDelivered()` используют тот же список
Email + Telegram + MAX + VK. Канал непосредственной доставки самой карты
получателю остаётся отдельной бизнес-логикой и не смешивается с уведомлением
покупателю.

### Брошенная корзина

Заменить `resolveChannel()` на `resolveChannels()` и отправлять шаг во все
доступные каналы. Добавить MAX. Для Email использовать созданный шаблон
`resources/views/emails/abandoned-cart.blade.php`, для мессенджеров — plain text.

Ручная отправка:

- при явно выбранном канале сохраняет текущее поведение;
- без выбранного канала отправляет во все доступные целевые каналы.

### Возврат товара в наличие

Сохранить текущее поведение, перевести получение адресатов на общий резолвер,
не меняя момент события.

### День рождения

Перевести обе ветки команды на общий резолвер, включить MAX и VK. WhatsApp не
добавлять в новую целевую модель.

## Модель данных для коммуникаций корзины

Изменить уникальность `cart_communications`:

```text
было:  cart_id + step
станет: cart_id + step + channel
```

Для ручных отправок `step = NULL`; антиспам остаётся по корзине и временному
окну. Перед миграцией проверить существующие дубли и особенности NULL в MySQL.

Статусы должны отражать реальное состояние доставки:

- `queued` — job поставлен в очередь;
- `sent` — канал подтвердил успешную отправку;
- `failed` — попытки исчерпаны.

Не помечать коммуникацию `sent` сразу после `dispatch()`.

## Критерии приёмки

- Клиент с Email, Telegram, MAX и VK получает каждое целевое событие во всех
  четырёх каналах.
- Клиент с частью контактов получает уведомления только в доступные каналы.
- Сбой одного канала не мешает остальным.
- Нет SMS и WhatsApp в новой транзакционной матрице.
- Один и тот же шаг брошенной корзины отправляется максимум один раз на канал.
- В `cart_communications` виден отдельный результат каждого канала.
- Уведомления о заказах и корзинах видны оператору в соответствующей истории
  переписки с `order_id` или `cart_id`.
- Email использует HTML-шаблон, мессенджеры получают читаемый plain text.
- Повтор команды/scheduler/job не создаёт дубли сообщений.

## Вне рамок

- Реализация SMS-провайдера.
- Возврат WhatsApp в виджет или транзакционную матрицу.
- Маркетинговые массовые рассылки, не привязанные к конкретному событию клиента.
- Изменение таймингов цепочки брошенной корзины (24 ч / 72 ч) без отдельного
  решения.
